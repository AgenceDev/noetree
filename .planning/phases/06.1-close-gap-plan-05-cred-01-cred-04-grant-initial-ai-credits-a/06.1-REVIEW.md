## Summary

Reviewed the `grantInitialCredits` mutation and its integration into `processWebhookEvent`'s
subscription-mode `checkout.session.completed` branch, plus the full contents of
`convex/aiCredits.ts` and `convex/stripeWebhooks.ts` (both files are read wholesale, not just
the diff hunks, per the standard-depth review scope).

The new `grantInitialCredits` logic itself is solid: the idempotency key is correctly suffixed
(`:credits-grant`) to avoid colliding with `upsertSubscription`'s raw-`stripeEventId` row (the
documented "landmine"), the reset-not-additive semantics are correct and tested, the new
`clerkUserId` anomaly guard prevents an `ArgumentValidationError`-to-500 for missing metadata,
and the two-mutation split (`upsertSubscription` then `grantInitialCredits`, each with its own
idempotency key) is retry-safe — a mid-sequence failure followed by a Stripe retry will correctly
short-circuit the already-applied mutation and complete the missing one. Test coverage for the
new behavior (insert path, patch/reset path, idempotency replay, the landmine regression, and the
D-01 re-subscription case) is thorough at both the `aiCredits.ts` unit level and the
`stripeWebhooks.ts` integration level.

No blocker-level defects were found in the code added by this phase. The items below are
pre-existing gaps in the surrounding file that this phase's own defensive pattern (the new
`clerkUserId` guard) highlights by contrast, plus minor quality/duplication notes.

## Warnings

### WR-01: Adjacent required-string args (`stripeCustomerId`/`stripeSubscriptionId`) are left unguarded against `undefined`, unlike the new `clerkUserId` guard

**File:** `convex/stripeWebhooks.ts:103-128` (subscription-mode `checkout.session.completed`) and `convex/stripeWebhooks.ts:146-166` (`customer.subscription.updated`)

**Issue:** This phase added a guard (`stripeWebhooks.ts:96-101`) that returns a clean
`{ anomaly: "missing clerkUserId" }` instead of letting an `undefined` `clerkUserId` reach
`upsertSubscription`'s validator (which would throw an uncaught `ArgumentValidationError` →
surfaced as a 500 → endless Stripe retries). The same class of gap still exists two lines later
for `stripeCustomerId` and `stripeSubscriptionId`:

```ts
const stripeCustomerId =
  typeof session.customer === "string"
    ? session.customer
    : session.customer?.id; // undefined if session.customer is undefined
const stripeSubscriptionId =
  typeof session.subscription === "string"
    ? session.subscription
    : session.subscription?.id; // undefined if session.subscription is undefined
```

`upsertSubscription`'s args validator declares both as required `v.string()` (not
`v.optional`) — see `convex/subscriptions.ts:26-27`. If either resolves to `undefined` (a
malformed or unusual event payload), the call throws before the handler's own `!args.clerkUserId`
anomaly check ever runs, producing exactly the 500-and-retry-loop failure mode this phase's new
guard exists to prevent. The same pattern recurs in `customer.subscription.updated`
(`stripeWebhooks.ts:146-150`), where `stripeCustomerId` is computed from `subscription.customer`
the same way and fed into the same required-string arg.

In practice Stripe should always populate these fields for these event types, so this is a
defensive-coding gap rather than a proven reachable crash — but it is the same landmine class the
new `clerkUserId` guard was added to close, left open one field over.

**Fix:** Add the same anomaly-return pattern used for `clerkUserId`:

```ts
if (!stripeCustomerId || !stripeSubscriptionId) {
  console.error(
    `checkout.session.completed (subscription) anomaly: missing customer/subscription for stripeEventId ${args.event.id}`,
  );
  return { anomaly: "missing customer or subscription" };
}
```

placed before the `ctx.runMutation(internal.subscriptions.upsertSubscription, ...)` call, and
analogously in `customer.subscription.updated`.

## Info

### IN-01: Non-constant-time secret comparison in `processWebhookEvent`

**File:** `convex/stripeWebhooks.ts:33`
**Issue:** `args.secret !== process.env.INTERNAL_WEBHOOK_SECRET` is a plain string comparison,
which is not constant-time and is theoretically vulnerable to a timing side-channel attack on the
shared secret. `processWebhookEvent` is a public `action` (not `internalAction`), so it is
reachable directly by any caller holding the Convex deployment URL, not only via the intended
`route.ts` → action call path — the shared secret is the only authorization boundary. This is
pre-existing (not introduced by this phase) and practically low-risk given typical network jitter,
but worth hardening given the secret is the sole gate on this endpoint.
**Fix:** Use a constant-time comparison, e.g. Node's `crypto.timingSafeEqual` (with a length check
first, since `timingSafeEqual` throws on length mismatch), or hash both sides with a keyed HMAC
before comparing.

### IN-02: Duplicated reset-and-record logic between `resetCredits` and `grantInitialCredits`

**File:** `convex/aiCredits.ts:161-222` and `convex/aiCredits.ts:236-287`
**Issue:** `resetCredits` and `grantInitialCredits` both implement the identical
patch-or-insert-to-`MONTHLY_CREDIT_QUOTA` → insert `creditTransactions` "reset" row → insert
`processedStripeEvents` row sequence, differing only in how the idempotency key is derived and
how `clerkUserId` is resolved (via subscription join vs. direct arg). This is the same kind of
duplication the file already avoids for the deduction path via the shared `applyDeduction`
helper (`aiCredits.ts:19-57`).
**Fix:** Extract a shared `applyCreditReset(ctx, clerkUserId)` helper (mirroring
`applyDeduction`) that both `resetCredits` and `grantInitialCredits` call after each resolves its
own `clerkUserId` and idempotency key, so the reset-and-record behavior only has one implementation
to keep correct.

### IN-03: Intentionally-unreachable branches with no direct test coverage

**File:** `convex/aiCredits.ts:40-49` (insert branch inside `applyDeduction`) and
`convex/aiCredits.ts:106-120` (refund branch inside `runAiAction`)
**Issue:** Both branches are well-documented as intentionally unreachable scaffolding (the
`applyDeduction` insert branch can never execute because `balance < amount` always throws first
when there's no existing row; the `runAiAction` refund branch is dead while `actionSucceeded` is
hardcoded `true`). Since neither branch is exercised by any test, a future edit that
inadvertently makes them reachable (e.g., changing the deduction-throw ordering, or wiring in a
real LLM call that can fail) would ship without any test verifying the branch's actual behavior.
**Fix:** No action required now, but when `actionSucceeded` is wired to a real result (per the
comment's own stated plan), add a test that forces the refund path and asserts the balance is
restored and a `refund` transaction is recorded, rather than relying on the current
"allows creditTransactions rows with type 'refund'" schema-only test.

### IN-04: Magic number for the pay-per-use topup credit amount

**File:** `convex/stripeWebhooks.ts:65`
**Issue:** The `amount: 50` passed to `addCredits` for a `mode: "payment"` checkout session is a
bare literal, unlike `MONTHLY_CREDIT_QUOTA` in `aiCredits.ts`, which is a named constant used
consistently by `resetCredits`/`grantInitialCredits`.
**Fix:** Introduce a named constant (e.g. `TOPUP_CREDIT_AMOUNT = 50`, exported from
`aiCredits.ts` alongside `MONTHLY_CREDIT_QUOTA` or defined locally in `stripeWebhooks.ts`) so the
value has one place to change and a self-documenting name.
