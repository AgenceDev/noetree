# Phase 06.1: Close gap: PLAN-05/CRED-01/CRED-04 — grant initial AI credits at Pro checkout - Context

**Gathered:** 2026-07-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Grant a new Pro subscriber their initial 100 AI credits at the moment `checkout.session.completed` (subscription mode) confirms their Stripe Checkout — closing the gap found by the v1.0 milestone audit's integration check. Today, `convex/stripeWebhooks.ts`'s `checkout.session.completed` subscription branch only calls `internal.subscriptions.upsertSubscription`; the only credit-granting code path is `invoice.paid` gated to `billing_reason === "subscription_cycle"`, which explicitly excludes the initial `subscription_create` invoice. Net effect: a brand-new Pro subscriber sees a `0`/`null` credit balance and their first AI action throws `INSUFFICIENT_CREDITS`, routing them to the "buy more credits" dialog instead of delivering the plan they just paid for.

This phase closes that one gap only. It does not touch: the recurring monthly reset (`invoice.paid`/`subscription_cycle`, already correct), the deduction/top-up machinery (Phase 5, already correct), or the Settings page display (Phase 6, already correct) — all three were independently confirmed WIRED by the audit's integration checker.

</domain>

<decisions>
## Implementation Decisions

### Re-subscription Grant Behavior

- **D-01:** When a lapsed Pro subscriber re-subscribes (a new `checkout.session.completed`, subscription mode, fires again for a `clerkUserId` that may still have an `aiCredits` row with a leftover balance), the initial grant **resets the balance to exactly 100** — it does not add 100 on top of any leftover balance. This matches the existing monthly-renewal semantics in `resetCredits` (`balance: MONTHLY_CREDIT_QUOTA`, not `balance +=`) and avoids a minor gaming vector (cancel right before renewal, resubscribe, stack credits).

### Backfill Scope

- **D-02:** **No backfill script this phase.** Any Pro subscriber who checked out before this fix ships and is currently stuck at 0 credits self-heals at their next monthly renewal (the existing `invoice.paid`/`subscription_cycle` → `resetCredits` path already works correctly and is unaffected by this gap). Appropriate because Stripe is still in test-mode for this project — no real paying customers are currently affected. Fix-forward only: this phase changes behavior for checkouts completed _after_ the fix ships.

### Idempotency Landmine (Claude's Discretion — flagging for planner/researcher awareness, not a product decision)

- **Landmine found during context-gathering:** `processedStripeEvents` is a single table keyed only by `stripeEventId` (not `stripeEventId` + action). `upsertSubscription` already inserts a `processedStripeEvents` row for the `checkout.session.completed` event's `stripeEventId` (`convex/subscriptions.ts:80-84`). If the new credit-grant call reuses the **same** `stripeEventId` as its own idempotency key (the way `resetCredits`/`addCredits` currently check `processedStripeEvents` by `stripeEventId`), it will find that row already inserted by `upsertSubscription` and silently no-op — **the credit grant would never fire, and this would look like nothing is wrong** (webhook still returns 200, subscription still activates correctly, only credits stay missing). The planner/researcher must design around this — e.g., a distinct idempotency key (such as a suffixed `` `${event.id}:credits-grant` ``) for the credit-grant write, or a dedicated internal mutation whose idempotency check is scoped to `(clerkUserId, "initial-grant")` rather than reusing the raw Stripe event ID collision-prone with the subscription write.
- Exact mutation name/shape (new `grantInitialCredits`-style mutation vs. reusing `resetCredits` with a modified idempotency key vs. another approach) is left to the planner.
- Exact test coverage approach (unit test on the webhook dispatcher's subscription branch, concurrency/duplicate-delivery test) is left to the planner, following the existing test patterns in `convex/stripeWebhooks.test.ts` and `convex/aiCredits.test.ts`.

</decisions>

## Existing Code Insights

### Reusable Assets

- `convex/aiCredits.ts` `resetCredits` — closest existing precedent for "set balance to MONTHLY_CREDIT_QUOTA (100)" semantics (D-01 requires this exact behavior, not additive)
- `convex/stripeWebhooks.ts`'s payment-mode branch (lines 46-71) — structural precedent for calling a credit mutation from within `checkout.session.completed`, including its missing-`clerkUserId` anomaly guard pattern

### Established Patterns

- Convex mutations are transactional per-call; `processedStripeEvents` check-and-insert happens inside the same mutation as the state write (Phase 2 D-14) — the new grant call must follow this same shape, with an idempotency key that does NOT collide with `upsertSubscription`'s own `processedStripeEvents` row for the same `stripeEventId` (see landmine above)
- Anomaly-not-throw convention: unresolvable `clerkUserId` logs via `console.error` and returns `{ anomaly: ... }`, never throws (Phase 2 D-12) — the new grant call should follow this if it needs its own guard

### Integration Points

- `convex/stripeWebhooks.ts` — subscription branch of `checkout.session.completed` (around line 98, alongside/after the `upsertSubscription` call)
- `convex/aiCredits.ts` — either extend `resetCredits`'s call signature/guard to accept being invoked from this new call site, or add a new internal mutation
